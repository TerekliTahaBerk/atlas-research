# Atlas approved recovery execution tools

These dated operator tools executed only the user-approved Atlas development target `hgngonpirctrwbckhbmy` on 2 November 2026. They are not a generic backup service and do not grant new authorization. See [the execution record](../../docs/operations/A01_HOSTED_EXECUTION_2026-11-02.md) before use.

All credentials, actual receipts and ciphertext live outside Git under the approved owner-only recovery directory. Never print protected configuration, decrypted archives, Auth rows, sessions, provider keys or diagnostics. `keychain.swift get` must be captured/piped directly; never run it with terminal output. Public certificate/recipient material is not a private identity.

- `capture.py`: exact target, owner-only files, verify-full, pinned master/12 hashes/3 installed baseline, empty Storage/Vault preflight; holds one read-only exported snapshot and streams six exports to age. Refuses today's now-migrated source baseline; a new capture requires a new reviewed inventory/approval record.
- `restore.py`: isolated loopback target only, source-role references and managed compatibility patch, streamed in-memory restore. `--verify-existing` was used to investigate the initial disposable restore before acceptance; accepted receipts prevent replacement. Exact data/security comparisons, CHECK expression reparse and actual FK orphan probes. Supabase vendor default browser grants are removed on this destination only.
- `metadata.py`: source read-only structural comparison; only four pinned, reviewed missing Auth indexes may be recreated on the isolated destination. Pins expected vendor history differences and otherwise rejects drift.
- `start-acceptance.py`, `session-cookies.mjs`, `acceptance.py`: after exact original hashes pass, invalidate clone sessions, use independent local Auth signing/passwords, internal mailbox delivery and normal provider sessions, non-owner Atlas web reads and outsider/anonymous denial. No source user/session mutation or fabricated user JWT. The two signed local bootstrap API keys are service configuration, not user identities.
- `finalize.py`: require independent database, application and structural evidence; verify ciphertext integrity, real empty Storage inventory, internal Docker networking and loopback bindings; record actual elapsed wall time and fixed expiries. No scheduled cleanup is implied.
- `rehearsal-copy.py`, `rehearse-migrations.py`: preserve the accepted original restore; create a separate local rehearsal database with original encrypted data/history, then normal Prisma status/deploy/status/repeat-deploy. No reset, history edit or resolve. Destination database owner must match source postgres so `pg_database_owner` resolves correctly.

The local compose/configuration and bootstrap files are protected operator state, not committed secret-bearing examples. Official PG17.11, Auth and Storage images, the reviewed Storage cloud/local differences, encryption custody and expiry limitations are documented in the execution record. G2 is evidence of one real capture/restore, not offsite DR or continuous backup.

`../activation/deploy-approved.py` is the separately approved G3 execution. It refuses a source history other than the exact three-entry baseline, requires accepted recovery/rehearsal and the protected user approval record, validates all pinned hashes, and captures before/after evidence encrypted. Its temporary Linux environment file contains an owner credential and must not be logged or committed. The Linux tool image uses the official pinned Node base plus required OpenSSL; engine downloads must match the published Prisma checksum recorded in the execution report. A different migration batch, target or environment needs a new review/approval, not editing the guard to force it through.
