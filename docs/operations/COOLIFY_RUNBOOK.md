# Atlas Coolify runbook

Only new Atlas resources in **yula.co / production**. Keep existing server/proxy/networks/volumes/apps unchanged. Do not enable automatic deployment before a release candidate has passed the local gate. The canonical production source is main after the verified slice is squash merged; a reviewed candidate branch can be tested explicitly before promotion. Never deploy an unverified moving head.

1. Run `npm ci`, install the pinned Playwright browser with `npx playwright install chromium`, then commit the candidate and run `npm run verify:release`. Record its exact SHA/image IDs. This uses only random, loopback-only local fixtures; never substitute a live DB URL.
2. In the existing yula.co environment create a new **Git-based Docker Compose Application** from this public repository, candidate branch and `/compose.coolify.yaml`. Use normal managed Compose, not Raw mode. Name it Atlas Research. Assign a domain to `web` only, internal port 3000. Leave all other services without domains/host ports. Keep predefined cross-resource networking disabled. Confirm Coolify preserves the internal backend and one-shot dependencies before deployment.
3. Set build arguments to **Managed manually in Dockerfile**. The only public build argument is `ATLAS_SOURCE_COMMIT`, matching `ATLAS_RELEASE`/the verified SHA. Never supply secret build arguments or copy env files into the context.
4. Coolify generates independent 32-byte hex values through the SERVICE_HEX_64_ATLAS* variables declared in Compose. These map to the dedicated DB roles and Better Auth secret inside their own processes. Keep generated values in the Atlas resource secret store; never reveal/copy them to chat/Git/terminal history. Values must remain stable across restarts. A changed bootstrap password does not rotate an existing DB role; rotation is a separate reviewed operation.
5. Set APP_ORIGIN to the actual HTTPS origin. Set SMTP_HOST/PORT/SECURE, SMTP_USER/PASSWORD and MAIL_FROM for the chosen sender. Web receives public mail config and queue credentials; only mail receives SMTP credentials. Mail never receives AUTH_DATABASE_URL; neither web nor mail receives migration/admin/backup secrets. Bootstrap gets admin plus initial role values, then exits; migration gets only its connection, then exits. Confirm this separation in deployed process environments without printing their values.
6. Use caps in Compose (web 512 MiB, DB 1 GiB, mail 256 MiB) as limits, not a claim of available capacity or performance. Check existing capacity read-only and build headroom. Do not change host settings, existing workloads or purchase capacity. Stop and resolve inadequate capacity rather than risking those workloads.
7. Before admitting real data, select and configure a host-independent encrypted backup destination/credential and retain recovery material outside this host. Local volume copies are not sufficient. Use the [fenced set contract](../COOLIFY_PLAN.md): drain/fence Atlas writes and mail, `pg_dump` 18 using the backup credential, manifest+immutable files (only a synthetic text file in Phase 01), encrypt, transfer and verify remote bytes/hash, then resume. Do not infer file backup from DB backup. Daily ≤24h RPO, ≤4h RTO and 7 daily/4 weekly/3 monthly retention are proposed targets requiring confirmation. No provider or paid subscription is selected implicitly.
8. Deploy Atlas only. Observe bootstrap exit 0, migration exit 0, web/mail healthy and expected schema `202611090004_operations`. No container may migrate on every web restart. Verify actual remote CPU architecture/image digest; local ARM64 evidence does not establish AMD64 runtime behavior.
9. Verify HTTPS/cookie Secure+HttpOnly+SameSite, origin denial, no client-supplied x-real-ip rate-limit bypass, registration and real verification/reset delivery, exact-recipient invitation, two-account collaboration, unrelated-team denial and current-session revocation. Keep test addresses/tokens/passwords in memory or restricted env only. Screenshots/logs must be synthetic/redacted.
10. Restart only Atlas web/mail/DB and observe persisted data. Retrieve the encrypted remote set into a fresh isolated restore target, provision roles, restore owners/ACL/policies and verify scoped data/file hashes. A new cluster's restore admin credential is an operations-only secret. Never rehearse on another application's DB. Record elapsed time, data point, counts and RPO/RTO limits.
11. Retain a known compatible image before promotion. Roll back only its image with the same preserved data, then repeat readiness/auth/two-team smoke. Migration 004 makes pre-operations P01-4 mail code incompatible; do not label it a rollback candidate. If schema compatibility is unknown, use forward fix or a separately reviewed fenced restore; never silently run reverse migrations.

Automatic merge/deploy, backup destination setup, external SMTP/TLS and live rollback are not established by the local gate. Record observed results in PHASE_01_HANDOFF before closing G01. No Phase 02 module is part of this runbook.
