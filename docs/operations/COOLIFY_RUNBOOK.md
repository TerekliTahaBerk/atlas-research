# Atlas Coolify runbook

Only new Atlas resources in **yula.co / production**. Keep existing server/proxy/networks/volumes/apps unchanged. Do not enable automatic deployment before a release candidate has passed the local gate. The canonical production source is main after the verified slice is squash merged; a reviewed candidate branch can be tested explicitly before promotion. Never deploy an unverified moving head.

Current owner-selected preview: temporary Coolify HTTPS domain, MAIL_DELIVERY=disabled, no S3, with the explicitly requested first identity. This permits limited owner access; it does not close email or independent-backup G01 requirements. Registration/recovery/email invitations show unavailable and no messages are sent. Keep verification enforcement intact. The full profile below becomes applicable when those features are explicitly enabled.

The owner subsequently requested a specific first login without email delivery. The optional **migration-only** initial-identity step accepts `ATLAS_INITIAL_USER_ACK=owner-requested-first-identity`, `ATLAS_INITIAL_EMAIL` and `ATLAS_INITIAL_PASSWORD` through Atlas secrets. It runs after migrations, only as `atlas_migrator` against the dedicated Atlas database, locks the user table and creates an identity only when it is empty. It uses Better Auth's native password hash, creates no session and grants no workspace/project membership. This one owner-asserted identity is marked verified by the operator; it is not evidence of mailbox verification or SMTP delivery. The operator-supplied initial credential can use Better Auth's base eight-character minimum; public account creation/recovery retains its 12-character policy. Existing identities/passwords are never replaced, even on repeated deployment. Remove all three values from Coolify after the one-time setup, then redeploy and verify normal sign-in. Never commit these values or put them in a shell command/log. They are supplied to neither web nor mail.

Coolify 4.6 managed Compose unconditionally adds its global `.env` as an `env_file` to every service. This was observed in the new Atlas web container and verified in [the vendor deployment source](https://github.com/coollabsio/coolify/blob/v4.6.0/app/Jobs/ApplicationDeploymentJob.php). Plain empty values can also be replaced by legacy stored values in [the parser](https://github.com/coollabsio/coolify/blob/v4.6.0/bootstrap/helpers/parsers.php). The Compose isolation anchor therefore masks all source secrets and privileged destination keys with an explicit empty interpolation, then each process overrides only its own allowed fields. Keep `ATLAS_ISOLATION_EMPTY` empty. Web/mail configuration rejects nonempty privileged fields in production. `verify:compose` reproduces global env-file injection with synthetic secrets and verifies all six process environments (including Phase 02 files). After deployment inspect only credential **presence booleans/role names**, never values; forbidden nonempty keys must be absent. Repeat after any Coolify/template update or new secret. Coolify also attaches its application management network; the backend's internal flag does not claim that the platform adds no other network. No database host port is allowed.

1. For the current owner-authorized Phase 02 release run typecheck/lint/build, `test:library`, `verify:compose` and the short final browser journey; record the exact SHA. The comprehensive `verify:release`/restore/rollback review remains before beta. This uses only random, loopback-only local fixtures; never substitute a live DB URL.
2. Use the existing **Atlas Research** Git-based Docker Compose Application in yula.co; select reviewed main and its exact commit, then Reload Compose for `/compose.coolify.yaml`. Do not create a replacement app or database. Use normal managed Compose, not Raw mode. Name it Atlas Research. Assign a domain to `web` only, internal port 3000. Leave all other services without domains/host ports. Keep predefined cross-resource networking disabled. Set this Atlas application’s custom build command to `docker compose --parallel 1 build`; Next build workers are capped at two and the build-stage Node heap at 1 GiB. These are application build limits, not host changes. Confirm Coolify preserves the internal backend and one-shot dependencies before deployment.
3. Set build arguments to **Managed manually in Dockerfile**. The only public build argument is `ATLAS_SOURCE_COMMIT`, matching `ATLAS_RELEASE`/the verified SHA. Never supply secret build arguments or copy env files into the context.
4. Coolify generates independent 32-byte hex values through the SERVICE_HEX_64_ATLAS* variables declared in Compose. These map to the dedicated DB roles and Better Auth secret inside their own processes. Keep generated values in the Atlas resource secret store; never reveal/copy them to chat/Git/terminal history. Values must remain stable across restarts. A changed bootstrap password does not rotate an existing DB role; rotation is a separate reviewed operation.
5. Set APP_ORIGIN to the actual HTTPS origin. For the current preview set MAIL_DELIVERY=disabled and leave SMTP values empty. For a later SMTP-enabled profile set MAIL_DELIVERY=smtp and provide SMTP_HOST/PORT/SECURE, SMTP_USER/PASSWORD and MAIL_FROM for the chosen sender. Web receives public mail config and queue credentials; only mail receives SMTP credentials. Mail never receives AUTH_DATABASE_URL; neither web nor mail receives migration/admin/backup secrets. Bootstrap gets admin plus initial role values, then exits; migration gets only its connection, then exits. Confirm this separation in deployed process environments without printing their values.
6. Use caps in Compose (web 512 MiB, DB 1 GiB, mail 256 MiB, files 384 MiB) as limits, not a claim of available capacity or performance. Check existing capacity read-only and build headroom. Do not change host settings, existing workloads or purchase capacity. Stop and resolve inadequate capacity rather than risking those workloads.
7. Deferred by owner until the pre-beta review: select and configure a host-independent encrypted backup destination/credential and retain recovery material outside this host. Local volume copies are not sufficient. Use the [fenced set contract](../COOLIFY_PLAN.md): drain/fence Atlas writes and mail, `pg_dump` 18 using the backup credential, manifest+immutable files (only a synthetic text file in Phase 01), encrypt, transfer and verify remote bytes/hash, then resume. Do not infer file backup from DB backup. Daily ≤24h RPO, ≤4h RTO and 7 daily/4 weekly/3 monthly retention are proposed targets requiring confirmation. No provider or paid subscription is selected implicitly.
8. Deploy Atlas only. Observe bootstrap exit 0, migration exit 0, web/mail/files healthy and expected schema `202611090005_library`. No container may migrate on every web restart. Verify actual remote CPU architecture/image digest; local ARM64 evidence does not establish AMD64 runtime behavior.
9. The following comprehensive checks are deferred before beta; short Phase 02 private-file denial still applies. Verify HTTPS/cookie Secure+HttpOnly+SameSite, origin denial, no client-supplied x-real-ip rate-limit bypass, registration and real verification/reset delivery, exact-recipient invitation, two-account collaboration, unrelated-team denial and current-session revocation. Keep test addresses/tokens/passwords in memory or restricted env only. Screenshots/logs must be synthetic/redacted.
10. Deferred comprehensive recovery review: restart only Atlas web/mail/DB and observe persisted data. Retrieve the encrypted remote set into a fresh isolated restore target, provision roles, restore owners/ACL/policies and verify scoped data/file hashes. A new cluster's restore admin credential is an operations-only secret. Never rehearse on another application's DB. Record elapsed time, data point, counts and RPO/RTO limits.
11. Deferred live rollback review: retain a known compatible image before promotion. Phase 02 revision 005 requires compatible web/mail/files images; pre-005 readiness code is not a verified rollback candidate. Roll back only its image with the same preserved data, then repeat readiness/auth/two-team smoke. Migration 004 makes pre-operations P01-4 mail code incompatible; do not label it a rollback candidate. If schema compatibility is unknown, use forward fix or a separately reviewed fenced restore; never silently run reverse migrations.

Automatic merge/deploy, backup destination setup, external SMTP/TLS and live rollback are not established by the local gate. Record observed results in PHASE_01_HANDOFF before closing G01. Phase 02 adds only `atlas-private-files` and the bounded files service. Keep the existing `atlas-postgres` volume and all generated identity/database secrets stable. See ADR 0004 and the Phase 02 handoff.
