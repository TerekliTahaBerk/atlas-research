# Authentication

Phase 01 uses `@supabase/ssr` and the compatible `@supabase/supabase-js` release pinned in the lockfile. The supported server flow follows [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client) and the installed Next.js 16 Proxy/cookie documentation.

`POST /api/v1/auth` validates an action union: signup, signin, reset, password, logout, google. Signup has confirmation and a 12–128-character policy, with native live-form constraints and safe field-specific server validation messages; Supabase alone handles passwords. Registration/recovery responses avoid account enumeration. Passwords clear after attempts; other form values remain. A successful login keeps the submit button disabled and announces destination loading until navigation replaces the form. `auth.getUser()` verifies every protected actor and rejects anonymous/unverified identities. Browser-provided user IDs or metadata roles are never permission inputs. Proxy refreshes SSR cookies; pages and services independently verify sessions. Private responses are no-store. Cookie Secure follows the configured HTTPS origin, SameSite=Lax, path=/; HttpOnly is not forced on Supabase cookies because the supported browser SSR client may need them. Browser clients use cookies, not localStorage.

`/auth/callback` exchanges a PKCE code, verifies the returned identity and uses a local return allowlist. Error/cancel/missing/expired callbacks return to login with accurate failure feedback. Recovery uses a short-lived, signed HttpOnly marker bound to the verified identity; password update verifies the user again, consumes the marker, updates through Supabase and signs out. Configure Supabase email templates/redirect allowlists for this PKCE flow. A recovery link must open in the browser that requested it; a missing verifier requires requesting a new link.

Google is disabled unless `ATLAS_GOOGLE_OAUTH=true` and the isolated Supabase project actually has Google configured. ORCID and institutional SSO remain unavailable. No OAuth result is fabricated. Auth operations use both provider rate limits and PostgreSQL-backed global/keyed application limits. Failure of the rate store closes the operation. The conservative quotas are operational starting points, not measured production capacity.

Live pages use a per-request script nonce CSP. Style attributes remain allowed for the existing Radix/layout system. Eval is allowed only in development for Next tooling. HTTPS live deployments receive HSTS. Incoming development request logging is disabled so callback codes are not printed; configure hosted ingress/access-log redaction separately. Never upload Auth traces, mailbox contents, cookies, tokens or screenshots containing credentials.

Hosted verification remains a separate gate. After initially deferring it, the user opened the existing Atlas Supabase dashboard for inspection. Read-only inspection confirmed email signup/confirmation enabled, anonymous login disabled and Google disabled; no callback URLs were configured. The user confirmed the Atlas development target; database migration/runtime access, verified TLS, actual Auth settings and invalid-login rejection have now been checked. The explicitly approved loopback Site URL/callback allowlist is saved and reload-verified; actual hosted signup, user-confirmed email, saved full onboarding and persisted private-project logout/deep-link login now pass. Hosted recovery remains NOT RUN; Google is disabled. The disposable GoTrue/mail capture harness tests provider-compatible local flows separately from mocked-SDK boundary tests. The hosted journey proves confirmation delivery for that account, not general delivery capacity or hosted recovery/OAuth/revocation timing. Separate actual Prisma checks verify both approved pooler modes.
