# Authorization and database identity

The hierarchy and role matrix in [DATABASE](../DATABASE.md) remain authoritative. The central SQL capability evaluator is `atlas_private.allowed`; its actor-bound `can` and `capabilities` entry points serve policies, mutation guards and UI projections. An organization/workspace administrator has metadata authority, never implicit private-project access. Workspace-visible grants are read only; explicit project roles grant scoped writes. Active organization and workspace membership remain prerequisites even for project owners. Archived projects expose recovery metadata only to an eligible owner; archived ancestors hide all descendants.

The server sets verified `atlas.actor_id` and normalized verified `atlas.actor_email` with transaction-local `set_config(...,true)` inside the same Prisma transaction as protected queries. Supabase's `auth.uid()` is not assumed to exist on that SQL connection. Reused connections have no actor outside the transaction. [ADR 0013](../decisions/0013-phase-01-actor-context.md) records the trust boundary.

Runtime logins must be non-owner, NOSUPERUSER, NOBYPASSRLS, with membership in `atlas_runtime` and no migration-role membership. The service checks these properties before every transaction. Runtime has SELECT under RLS and EXECUTE on explicitly granted mutation/rate functions. Direct DML is ungranted and also has deny INSERT/UPDATE/DELETE policies. Browser `anon`/`authenticated` roles receive no domain table grants or private-schema execution. Do not expose `atlas_private` through the Data API.

Security-definer helpers avoid recursive RLS; fixed search paths and revoked PUBLIC execution constrain them. Mutations are an explicit privileged database boundary: fixed command cases, no dynamic SQL, resource resolution, live authorization, composite keys and transactional audit records. They use the migration principal internally; the normal connection itself never bypasses RLS. The server credential can set actor context and is therefore trusted infrastructure, not a browser credential. Runtime SQL possession or a compromised web server is outside this tenant-isolation proof.

Hierarchy writes serialize on one advisory transaction lock. This covers parent removal, ownership changes, invitation acceptance and personal provisioning. Removing a parent membership removes descendant grants only when it does not strand an active project owner. Personal owners/admins cannot be removed or demoted. Last organization/project owners cannot be removed/demoted; an owner first grants another eligible member ownership, then removes the old owner. Expected versions reject stale membership/container edits. Reads are not serialized. Revisit the conservative write lock when measured contention warrants finer-grained locks.

Revocation applies on the next protected database transaction. Previously rendered content is not retroactively erased, and no UI button is an authorization boundary. Hosted transaction-pooler behavior and session revocation timing remain explicit release tests.
