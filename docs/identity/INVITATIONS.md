# Invitations and memberships

Invitations target organization, workspace or project scope. Each has an intended normalized email, role, inviter, composite tenant keys, seven-day expiry, SHA-256 hash, acceptance/revocation timestamps and an audit event. The 256-bit random plaintext token is returned only once to the authorized inviter and is never stored in the database. Acceptance links keep it in a URL fragment; acceptance POSTs the token to the server, which hashes it before calling SQL. Tokens never go in browser storage or application logs.

Creation checks the target capability and role ceiling. Organization invitations allow MEMBER or ADMIN; only an organization OWNER may invite an ADMIN. Workspace invitations allow ADMIN/MEMBER/VIEWER under workspace administration. Project invitations require project OWNER and allow OWNER/EDITOR/VIEWER. Parent organization/workspace grants created by a narrower invitation are MEMBER. Existing parent/target memberships are retained; accepting an invitation does not overwrite an existing role. Change an existing role explicitly through membership management.

Acceptance locks the invitation and hierarchy, checks current inviter authority, active ancestors, verified recipient email, expiry, revocation and consumption. Wrong identity/expired/revoked/replayed/unknown tokens share the same non-leaking unavailable response. A transaction grants the necessary hierarchy and consumes the invitation once. Concurrent replay cannot duplicate memberships. Revocation is available to current scope administrators. Membership/ownership changes use expected versions and last-owner safeguards.

No transactional invitation-email provider is configured. Creation in production fails closed with an accurate explanation. `ATLAS_DEV_INVITATION_LINKS=true` enables one-time link display only on a loopback-origin development server, never `next start`/production. Auth verification/recovery email belongs to Supabase and is separate from application invitation delivery. No email delivery is claimed for development links.

The public `/invite` landing reveals no target metadata. Existing users sign in with their verified intended email. New users register, verify and complete personal setup, then reopen the original invitation link. The fragment remains in the original URL and is not persisted elsewhere. Success removes it from the address and opens the authorized target. Invalid links produce safe errors. Do not paste invitation links into analytics, screenshots or reports.
