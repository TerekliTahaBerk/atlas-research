# P01-3 — Tenancy and lifecycle

Shared/personal workspaces, explicit private project membership, owner/admin/editor/viewer roles, archive, reversible project deletion (30 days), owner transfer and revocation are implemented in domain services and strict private HTTP entries. Workspace governance never grants private project access. Creation and first owner are atomic; creation retries use a caller-generated request UUID. Fresh login (five minutes) is required for owner transfer/removal and deletion. Sign in again to satisfy this gate; no custom password verifier exists.

Migration `202611090003_tenancy` enables and forces RLS on every app table. Runtime cannot assume auth/migration/helper roles or perform DDL/TRUNCATE. Scope fields are immutable, and project/member/invitation/audit composite foreign keys prevent cross-workspace links. Workspace revocation deactivates all project memberships and refuses removal of the sole owner of any private project without exposing its title.

`atlas_policy` owns boolean permission/lock helpers with fixed search paths, no PUBLIC execution, no login and narrowly granted table privileges. PostgreSQL row-lock SELECTs also consult UPDATE policy visibility; readers therefore acquire shared locks through boolean helpers, then query data with ordinary runtime RLS. `atlas_lifecycle` is a separate NOLOGIN role owning only invitation preview/accept and workspace-revocation entry functions. It has no caller-supplied actor argument. Only the migrator can assume either helper role. Runtime uses transaction-local user **and live session** context; missing, expired and revoked context denies access. Workspace → project lock ordering serializes membership changes, with at most three transaction attempts on serialization/deadlock failures.

Invitations store SHA-256 hashes, expire in seven days and require the exact verified recipient. Acceptance atomically creates only base workspace membership and the permitted project role. It checks the issuer's current grant power, refuses inactive workspace recipients and cannot replay an old acceptance to restore revoked access. Only encrypted SMTP mail contains the raw token. Invitation and encrypted outbox insertion share one transaction. Dispatch checks the issuer session, current role and invitation status using the runtime connection before SMTP. Already dispatched mail cannot be recalled; the link remains subject to live authorization at acceptance. Auth mail still has the separate Better Auth/outbox transaction limitation recorded in P01-2. A dedicated queue DB credential is deferred to P01-5; no research-content worker is added.

All mutations require exact origin, JSON, bounded bodies, strict schemas and a DB-backed 60/minute per-user domain limit. Responses are private/no-store; raw SQL errors are normalized. Profile lookup is restricted to member IDs first selected through runtime authorization, under the scope lock. No global directory is exposed.

Verification: `npm run verify` (typecheck, lint, unit tests, real PostgreSQL integration, production build). The integration suite covers A01–A06/A08–A11/A13 for currently implemented identity/workspace/project resources: teams A/B; D workspace admin without project role; V viewer; live B revocation with a blocking shared read; concurrent final owners; wrong/expired/revoked/replayed/issuer-downgraded invitations; cancelled queued invitation mail; pool reuse and missing context; direct SQL role/DDL/TRUNCATE denial; FORCE RLS and composite FK checks independent of RLS. A07/A12 and PDF/export/search/version/AI portions of the matrix are NOT RUN/out of phase. UI, external SMTP, deployment and G01 remain open.
