# P01-5 — Deployment candidate and operations evidence

Status: local candidate verified; live Coolify acceptance pending. Target confirmed in Chrome: **yula.co / production** on the user's existing Coolify. The user explicitly requires that existing server, proxy, network and other application settings remain untouched. No server patches, runner, host reconfiguration or unrelated resource action is authorized by this slice. A new Atlas Compose Application is the only deployment scope.

`Dockerfile` pins the Node multi-platform index digest from `ops/images.json`; OpenSSL/CA certificates are explicit. Linux ARM64 builds passed with Node 24.21.0, npm 11.19.0 and OpenSSL 3.0.22. Image stages are `web` (Next standalone), `mail` and `migrator`; all run as `node` UID 1000. Image revision labels accept only the public candidate commit argument. No application secret or DB is needed during build. Docker build runs typecheck/lint/unit/build; the full release gate additionally runs disposable PostgreSQL and browser integration outside the production host. No paid Actions workflow or production runner exists.

Migration `202611090004_operations` separates encrypted mail into `ops.mail_outbox`: auth can no longer read the queue; queue can no longer read identity/project data; runtime can enqueue in its domain transaction but cannot read outbox payloads. `atlas_backup` has read/backup privileges, BYPASSRLS and default read-only transactions; its credential is not supplied to web/mail. `atlas_lifecycle` remains NOLOGIN, callable only through fixed authorized functions. Bootstrap checks that the DB is exactly `atlas`, creates only Atlas roles, rejects unexpected existing role privileges and never rotates an existing password. The separate migrator applies reviewed files; web startup never migrates.

`/health/live` is independent of DB availability. `/health/ready` fails closed unless the expected schema revision and a current mail-worker heartbeat are present. It returns only readiness/release/revision, never connection details. Mail stops dispatching after the current bounded SMTP operation on shutdown; leases allow recovery after an unclean stop. SMTP is at-least-once, not exactly-once.

`compose.coolify.yaml` defines a dedicated PostgreSQL 18.6 volume mounted at the PostgreSQL 18 parent path, internal backend network, explicit one-shot bootstrap→migration→web/mail dependency, resource caps, read-only application filesystems, tmpfs cache, dropped capabilities and no host ports. Only web gets a Coolify domain. One-shot `exclude_from_hc` keys are [documented Coolify extensions](https://coolify.io/docs/applications/builds/docker-compose); `npm run verify:compose` removes only those keys before standard Compose validation with dummy variables. Live Coolify parsing/routing is still an acceptance step. [Next standalone output](https://nextjs.org/docs/app/api-reference/config/next-config-js/output), [PostgreSQL image volume guidance](https://hub.docker.com/_/postgres).

PASS observed locally: Docker build; six PostgreSQL integration tests; complete `npm run verify` including browser flows; Compose validation; `npm run test:operations` on isolated Docker resources. The operations drill observes actual UID/role separation, DB/web restart persistence, live=200/ready=503 during DB outage, fenced `pg_dump` using the backup role, AES-256-GCM bundle roundtrip, restore into a fresh cluster with roles/owners/policies, synthetic file SHA-256 and two-team RLS after restore. The first successful restore+rollback interval was **4,643 ms** for two synthetic projects and one tiny text fixture; this is not a production RTO estimate. Fixture email verification is intentionally not asserted by this drill; real controlled SMTP/browser verification is a separate test.

Rollback drill promotes a distinct metadata revision of the same application/schema image, then restores the previous image and checks persisted access. It proves the local image-switch procedure, not compatibility of older application code. In particular pre-operations P01-4 expects the old outbox schema and is **not** an approved rollback image after migration 004. No reverse/destructive migration is automated. Local test DB ports are loopback-only; Docker allocates new random bindings on restart, which the harness observes and refreshes. Production PostgreSQL has no published port.

`npm run verify:release` requires a clean committed candidate, scans tracked files for obvious credentials/private-data extensions, runs all app checks, validates Compose, builds all three images with the exact commit label, runs the operations drill and writes ignored local evidence under `.atlas-local/`. This is a bounded pattern scan, not proof that every possible secret is absent. Exact final candidate/image identifiers are in that generated report and the PR evidence.

NOT RUN: deployment/TLS and real external SMTP delivery in Coolify; a host-independent encrypted backup destination; remote restart/persistence, external restore and live rollback. Read-only inspection found no yula.co project/environment/team shared variables and zero configured S3 backup destinations. No SMTP credential was opened or copied. Domain, usable SMTP and independent backup decisions must be concrete before live promotion. No purchase is made. G01 remains open.

Coolify draft resource **Atlas Research** was created in yula.co/production and its source pinned to the candidate branch/commit; it has not been deployed. Compose uses documented SERVICE_HEX_64_ATLAS* generators so role/session secrets are generated by Coolify without passing plaintext through chat or tool output. Only Atlas resource configuration is changed.
